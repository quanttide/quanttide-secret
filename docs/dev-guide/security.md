# 安全设计：客户端零知识实现

> 本文档说明量潮密码云如何实现"客户端零知识"（Zero-Knowledge）——服务端永不接触明文与密钥，以及主密钥的生成、使用与管理。
> 相关文档：[storage.md](./storage.md)（存储选型）、[transfer.md](./transfer.md)（传输架构）、[model.md](./model.md)（数据模型）。

## 1. 核心思想：信任根在客户端

零知识的本质是：**密钥只存在于客户端，服务端（FC + OSS）永不接触明文和密钥**。服务端保存的一切数据，在密码学上对服务端自己也是不可读的密文。

## 2. 密钥层次（当前单团队阶段）

```
主密码（用户记忆，仅在客户端内存）
   │
   ▼ Argon2id KDF（随机盐，参数随密文存储）
派生密钥（主密钥）
   │
   ▼ AES-256-GCM 加密/解密
密码内容
```

- 主密码**从不传输**、从不落盘、服务端无任何存储——服务端连密码哈希都没有
- 派生密钥只在客户端内存中短暂存在，解密完即释放
- 每次加密随机生成 `nonce` 与 `kdfSalt`，同一条目两次加密产生不同密文——服务端无法通过密文比对判断"是否是同一密码"

## 3. 主密钥管理

### 3.1 两层密码体系：登录密码 vs 主密码

本架构里有两层完全不同的"密码"，只有一层是必要的：

| 层 | 是什么 | 作用 | 谁验证 |
|----|--------|------|--------|
| **登录认证** | 外部子系统的账号密码 | 证明"你是谁"，换取 JWT | 外部子系统（服务端验证，可重置） |
| **主密码** | 本地解锁密码 | 派生解密密钥（口令即密钥） | **没人验证**——服务端无法验证、无法重置 |

关键点：**本系统不建账号、不存任何密码（连哈希都没有）**，用户身份由外部子系统 JWT 承载。所以：

- **不存在"密码库泄露"威胁**（没有密码库）
- 主密码**不登录任何东西**——它不是"账号密码"，而是"口令即密钥"（password-as-key）：`Argon2id(主密码, 盐) → 解密密钥`
- 主密码的作用是**本地钥匙**，而不是**通行证**；要让服务端读不到数据，就必须让解密钥匙只存在于用户脑子里（生物识别只是包一层，底层仍是主密码）

> 用户视角：记一个外部系统账号密码（登录）+ 一个主密码（解锁）。这是零知识的必然代价。

### 3.2 术语澄清：主密码 ≠ 主密钥

| 术语 | 是什么 | 存在哪里 |
|------|--------|---------|
| **主密码** | 用户记忆的高熵口令 | 只存在于用户大脑 |
| **盐（kdfSalt）** | CSPRNG 生成的随机串，每条目独立 | 随密文信封存储在 OSS（明文，不怕泄露） |
| **派生密钥（主密钥）** | `Argon2id(主密码, 盐)` 的输出 | **不存在于任何地方**——每次使用现派生，用完即弃 |

关键认知：**主密钥不是"被安全存储"的对象，而是"每次重新计算"的产物**。存储一个密钥就要保护一个密钥（密钥管理问题的递归），而"不存储、只派生"直接绕开了这个问题。

### 3.3 主密钥的全生命周期

```
① 生成：用户设置主密码（产品强制高熵策略）→ 客户端 CSPRNG 生成盐
② 派生：Argon2id(主密码, 盐) 高成本参数 → 派生密钥出现在客户端内存
③ 使用：AES-256-GCM 加密/解密条目 → 完成后内存中擦除
④ 存储：无。只有主密码（记忆）+ 盐（随密文存 OSS，本身无秘密）
⑤ 修改主密码：验证旧主密码 → 新盐 + 新派生密钥 → 重加密全部条目 → 旧盐作废
⑥ 丢失：不可恢复，靠 Emergency Kit 恢复机制（见 3.5）
```

- **派生**：Argon2id 的成本参数（迭代次数、内存占用）是抗暴力破解的关键——攻击者拿到密文 + 盐后要跑同样的 KDF，参数越高，每秒尝试次数越少
- **每次使用都重新派生**：解锁时派生一次，锁定时内存清零，不缓存（防止内存长期驻留密钥）
- **每条目独立盐**：每条目密钥互不相同，泄露一个条目的密文不影响其他条目；同一条目不同版本密文也不同

### 3.4 为什么服务端完全插不上手

- 主密码：从不传输，服务端连**密码哈希都没有**（不存密码，就没有密码库泄露问题）
- 盐：明文存储没关系——盐不是秘密，它的作用是让相同主密码派生出的密钥不同、并抵抗彩虹表
- 派生密钥：服务端拿不到主密码，盐在客户端本地，无法重现派生

所以**修改/重置主密码不可能通过服务端完成**——服务端没有可以"重置"的东西，这正是零知识的推论。

### 3.5 遗忘恢复机制（Emergency Kit）

零知识下"忘记主密码"必须靠**用户侧备份**，产品必须引导：

```
Emergency Kit（用户离线保存：打印纸质 / 加密文件）
├── 主密码（用户自己填写）
├── 账户信息（用户名、恢复码）
└── 使用说明
```

- **恢复码**：随机高熵字符串，与主密码一起参与派生（`Argon2id(主密码 + 恢复码, 盐)`）——即使主密码被键盘记录器窃取，攻击者仍缺恢复码，无法派生密钥；用户忘记主密码时，凭恢复码恢复
- **替代方案（可选）**：加密的密钥备份文件——用恢复码派生密钥加密"主密钥备份"，恢复时用恢复码解密
- 产品必须做：注册时强制引导生成 Emergency Kit，登录页提供恢复入口

### 3.6 受托恢复（Trusted Contacts，团队版）

个人版只有 Emergency Kit 一条路（备份给"一张纸"），企业场景（员工忘密码、离职交接）需要把恢复能力委托给**可信的人**而非纸面：

- **机制**：Shamir 秘密分享，恢复码拆成 n 份碎片分发给 n 位可信成员，任意 k 份（阈值 k ≤ n）可重构恢复码，少于 k 份在数学上得不到任何信息
- **流程**：设置时客户端拆分并分别加密分发 → 碎片存于各成员设备 → 恢复时凑齐 k 份碎片汇聚到用户客户端重构 → 设置新主密码
- **零知识保证**：服务端只转发加密碎片，永远看不到完整恢复码；任何单个成员只有碎片；即使服务端被攻破，攻击者还需同时攻破 k 位成员设备
- **安全权衡与缓解**：
  - 成员合谋 → 阈值设高（如 3/5）+ 选择真正信任的成员
  - 成员离职 → 支持重新分发（剔除后重新拆分，碎片轮换）
  - 恢复被滥用 → 每次恢复需用户本人配合 + 审计记录
- **与 1Password 管理员恢复对比**：1Password 由管理员持有恢复密钥（单点）；本方案 Shamir 碎片分摊（去中心化），不存在"一个管理员被收买就全完"的单点，成员间互相制约
- **理念渊源（HashiCorp Vault）**：Shamir 秘密分享正是 HashiCorp Vault 的核心机制——unseal 解封（密钥拆 N 份、凑 T 份解封）、recovery keys（auto-unseal 模式下的恢复密钥拆分）、rekey（重新生成并重新拆分碎片）、generate-root（凑齐碎片生成特权凭证）。本方案与 Vault 同源：**Vault 用 Shamir 保护"服务器的钥匙"（运维团队持有碎片），我们用 Shamir 保护"用户的钥匙"（可信同事持有碎片）**——机制相同，保护对象不同（基础设施 vs 人）。密码管理器同行中：1Password 用管理员恢复密钥（单点），Bitwarden 用紧急访问（延迟接管而非碎片），本方案更接近 Vault 的去中心化思路

### 3.7 威胁与缓解

| 威胁 | 影响 | 缓解 |
|------|------|------|
| OSS/FC 泄露密文 | 攻击者离线跑 Argon2id 暴力破解 | 高熵主密码 + 高成本 KDF 参数 + 恢复码双因子派生 |
| 键盘记录器/钓鱼窃取主密码 | 拿到主密码但无恢复码 | 恢复码作为第二因子（与主密码分开保存） |
| 在线暴力破解 | 撞 API | 服务端限流 + 外部子系统 2FA（提高在线门槛，但不保护离线密文） |
| 主密码相同/弱密码 | 字典攻击 | 强制强度策略 + 与已知泄露密码库比对 |
| 设备被木马入侵 | 明文在内存中被窃取 | 零知识不保护已失陷终端——只能靠设备侧安全（系统级） |

注意一个诚实的边界：**服务端 2FA 无法保护离线密文**——攻击者拿到密文后是在本地破解，不经过服务端。所以主密码强度和恢复码才是真正的防线。

### 3.8 团队版的主密钥角色演进

```
当前（个人版）：主密码 → 派生密钥 → 直接加密条目
团队版：       主密码 → 派生密钥 → 保护非对称私钥 → 私钥解包 DEK → DEK 加密条目
```

这个演进带来一个关键收益：**修改主密码的成本**。当前设计改主密码 = 重加密全部条目；团队版改主密码 = 只需重新加密一次私钥（条目仍用旧 DEK，不动）。这正是 1Password 改主密码秒完成的原因——也解释了为什么我们给团队版预留了信封加密结构（model.md 第 7 节）。

## 4. 数据流：明文与密文的边界

```
【客户端】                              【服务端】
明文密码 ──AES-256-GCM──> 密文信封 ──TLS──> FC（验签+代理）──> OSS 存密文
明文密码 <──AES-256-GCM── 密文信封 <──TLS── FC（代理读取）<── OSS 取密文
    ↑ 明文只在这一侧存在                    ↑ 这一侧永远只有密文
```

## 5. 服务端各组件"看到"什么

| 组件 | 能看到 | 看不到 |
|------|--------|--------|
| FC 应用服务 | 密文信封、明文元数据（id/name/时间戳）、谁在何时访问（审计） | 密码明文、派生密钥 |
| OSS | 密文信封（还被 SSE-OSS 二次加密） | 密码明文、派生密钥、甚至服务端加密前的密文形态 |
| 外部子系统（签发 JWT） | 用户身份（谁在访问） | 密码内容 |
| 审计日志 | 操作者、时间、对象 id | 任何明文内容 |

关键点：**FC 虽然经手每一条密文，但它没有密钥，密文对它只是无意义字节**。它做的校验（UUID、大小、schema）全部基于密文信封的外层结构，不涉及内容。

## 6. 攻击场景推演

| 攻击场景 | 结果 |
|----------|------|
| OSS 桶全量泄露（含访问凭证） | 攻击者拿到密文信封，无主密码无法派生密钥 → 不可解密；SSE-OSS 再加一道物理层保护 |
| FC 应用服务被攻破（RCE） | 攻击者能读密文、能读代码，但没有主密码 → 仍然不可解密 |
| 云厂商被取证/配合调查 | 服务端交出的只有密文和元数据，无明文可交 |
| 数据库（将来 PG）泄露 | 只有元数据/审计，无密钥无密文 → 无密码内容泄露 |
| **主密码被钓鱼/暴力破解** | **防线崩溃**——零知识架构唯一的阿喀琉斯之踵（见下） |

## 7. 边界：哪些"不是"零知识

1. **`name` 等元数据是明文**：信封里 `name` 明文存储（用于列表/搜索）。准确说法是**"内容零知识"**——密码内容不可见，但条目标题/时间戳服务端可见。若将来要求标题也保密，可把 name 移入 `encrypted` 负载，代价是失去服务端搜索能力（当前无服务端搜索，代价≈0）
2. **主密码强度 = 安全上限**：攻击者可离线拿密文 + 盐暴力破解，弱主密码可能被字典攻击。产品必须强制：高熵主密码要求 + Argon2id 高成本参数（迭代/内存）
3. **客户端设备是信任根**：用户设备被木马入侵时，明文在内存中仍可能被窃取——零知识保护"传输和存储"，不保护"已失陷的终端"
4. **忘记主密码 = 数据不可恢复**：没有"重置密码"通道（服务端无密钥可重置），只能靠 Emergency Kit 恢复——这是零知识的产品代价

## 8. 与团队版的衔接

当前是简化形态（单密钥派生）。上团队版后，零知识升级为**信封加密**（transfer.md / model.md 已预留结构）：

```
保险库密钥 DEK（随机生成）──用每个成员的公钥包裹──> 包裹密文存服务端
成员解密：拉取自己的包裹密文 → 私钥解包得 DEK → 解密密文条目
```

此时零知识扩展为"**团队零知识**"：服务端连 DEK 都看不到（只有公钥包裹的密文）；成员离开时轮换 DEK 即可让旧成员永久失去访问能力。**传输链路和信封结构不变**，只是密钥来源从"主密码派生"换成"私钥解包"。

## 9. Vault 的定位与边界

> 领域背景：README 领域边界包含"Vault 等密钥管理服务的接入规范"。本文明确 Vault 在本架构中的职责边界——**Vault 管"机器的钥匙"，客户端管"人的钥匙"，两条线不交叉**。

### 9.1 为什么 Vault 自身不是零知识

Vault 的信任结构决定了它能看到一切：

```
Vault 内部：
  主密钥（master key）——由 unseal key 解封后常驻内存
     │
     ├─ 派生密钥加密所有 KV 数据（存储加密）
     └─ transit 引擎持有加密密钥，明文进出 transit 接口

结论：Vault 进程、管理员、攻破 Vault 的人——都能解密 Vault 里的数据
```

- **KV 存储**：数据加密落盘，但 Vault 掌握 master key → 对 Vault 可读
- **transit 引擎**：客户端把明文发给 Vault 加密 → **明文经过服务端** → 服务端接触明文
- **unseal / root token**：管理员可以解封、可以 generate-root → 管理员的信任 = 数据的信任

| 维度 | Vault（服务端加密） | 客户端零知识（本架构） |
|------|---------------------|------------------------|
| 解密钥匙在谁手里 | **Vault / 服务端** | **用户客户端** |
| 服务端被攻破 | 数据**全部**可解密 | 只有密文，无密钥不可解 |
| 管理员/运维 | 信任他们 = 信任数据安全 | 不信任也没关系（他们看不到） |
| 攻击面 | 集中在 Vault 集群（大目标） | 分散到每个用户终端（无单点） |
| 被取证 | 能交出明文 | 只能交出密文 |

类比：Vault = 银行金库（银行有备用钥匙能开你的保险箱，它承诺不这么做，但钥匙在它手里）；零知识 = 只把**密封的盒子**存进金库（银行保管盒子，打开盒子的钥匙在你口袋里）。**零知识的定义是"数据拥有者持有唯一解密能力"，Vault 是"保管者持有解密能力"**——它把钥匙管得很好，但钥匙在它手里。

### 9.2 Vault 在架构中的职责（服务端密钥底座）

| 放 Vault | 理由 |
|----------|------|
| OSS 访问凭证（阿里云 secret engine 动态生成 STS） | 替代静态 AK/SK，短期凭证自动轮换，泄露面最小化 |
| JWT 签名/验签密钥（HS256，与 qtcloud-auth 共享 JWT_SECRET） | 集中托管 + 轮换 + 审计 |
| 数据库口令（团队版引入 PG 时） | 动态凭据，应用不持有静态密码 |
| transit 引擎（审计日志、元数据加密） | 服务端用 Vault 加解密而不接触密钥明文 |
| 部署凭据（FC 环境变量注入改 Vault Agent） | 消除 tfstate 明文落盘（README 待办） |

| 不放 Vault | 原因 |
|------------|------|
| **客户端主密码 / 派生密钥**（红线） | 进 Vault = 服务端能解密 = 零知识瓦解 |
| **密文信封对象**（secrets/<id>.json） | 是数据不是密钥，归 OSS（KV 存储替代不了对象存储的版本控制/生命周期） |
| **用户恢复码 / 受托恢复碎片** | 碎片属于"人"，进 Vault 变成"系统持有"，违背受托恢复初衷 |

**红线原则：客户端密钥绝不进 Vault**。Vault 的引入不改变零知识边界——它只是把服务端散落的密钥集中托管、动态化、审计化，与客户端零知识隔着一道永不跨越的密文边界。

### 9.3 Vault 与 KMS 的生态位关系（待引入）

Vault 在架构中替代的是"阿里云 KMS 3.0 密钥管理实例"这一生态位（服务端密钥底座）：

| KMS 的用途 | Vault 能否替代 | 说明 |
|-----------|---------------|------|
| 服务端密钥托管（OSS 凭证 / JWT 密钥 / DB 口令 / transit） | ✅ **完全替代** | Vault 主场，社区版免费，还多了动态凭据能力 |
| OSS SSE-KMS（bucket 服务端加密） | ❌ **不能替代** | OSS 内部加密选项，外部系统不识别；该层已由免费的 SSE-OSS 覆盖（见 storage.md） |

- Vault 社区版免费 vs KMS 3.0 实例 2,499 元/月起——正好补上砍掉 KMS 后服务端密钥底座的空缺
- **当前阶段：不落地，仅预留架构位**。等团队版（DB 动态口令）或私有化部署（数据主权）立项时再引入，届时在 manifests/terraform 落地（ECS + Raft 集群 + unseal 运维）
