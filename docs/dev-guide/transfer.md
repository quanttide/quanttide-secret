# 密码传输架构

> 本文档定义量潮密码云当前阶段（单团队、小数据量、忽略高并发、纯 OSS 存储、无附件）的传输架构。
> 前置：存储选型见 [storage.md](./storage.md)，数据模型见 [model.md](./model.md)。

## 1. 设计目标与核心原则

| 原则 | 说明 |
|------|------|
| **明文永不离开客户端** | 加密在客户端完成，传输链路中只有密文信封 |
| **应用服务作为唯一代理** | 客户端不直连 OSS，所有读写经应用服务 API，鉴权/校验/审计集中一处 |
| **无状态认证** | 用户在外部子系统，本系统不存用户、不建会话，每请求验签 |
| **传输全程加密** | 全链路 TLS 1.3 |
| **传输可审计** | 每次读写记录审计日志 |

## 2. 架构总览

```
外部子系统 ──签发 JWT (RS256/ES256)──> 客户端
客户端 ──Authorization: Bearer <JWT> + 密文信封──TLS 1.3──> 应用服务（验签 + 校验 + 代理读写 + 审计）
应用服务 ──STS 临时凭证──> 阿里云 OSS（secrets/<id>.json，版本控制 + SSE-OSS）
```

- **客户端**：加密/解密、本地缓存与索引
- **应用服务**：验签、请求校验、代理 OSS 读写、审计日志
- **OSS**：密文信封的存储（版本控制 + SSE-OSS 兜底）
- **无 PG**：当前阶段关系型需求归零，应用服务不依赖数据库

## 3. 认证：外部子系统令牌，无状态验签

用户在另一个子系统，本系统**不存用户、不建会话**：

```
① 外部子系统：签发 JWT（RS256/ES256，含 iss/aud/exp/scope）
② 客户端：请求头 Authorization: Bearer <JWT>
③ 应用服务：JWKS 公钥验签 → 校验 exp/aud/iss → 放行
```

| 项 | 设计 |
|----|------|
| 签名算法 | RS256 / ES256，由外部子系统私钥签名 |
| 公钥获取 | 应用服务缓存外部子系统 JWKS，定期刷新 |
| 防重放 | 短过期时间 + 时间窗口校验（单团队场景足够） |
| 授权规则 | 当前阶段：验签通过即可读写（单团队）；JWT 预留 `scope` 字段，将来细粒度权限无需改协议 |
| 登出/吊销 | 依赖 token 短过期自然失效；必要时通过外部子系统黑名单接口，当前阶段不做 |

## 4. 上传链路

```
① 客户端：明文密码 → Argon2id 派生密钥 → AES-256-GCM 加密 → 信封 JSON（model.md 结构）
② 客户端：POST /secrets（body = 信封 JSON）──TLS 1.3──> 应用服务
③ 应用服务：验签 → 校验（id 为 UUID、name 长度、信封大小 ≤ 64 KB、JSON schema）→ 记录审计
④ 应用服务：STS 临时凭证 PUT 至 OSS secrets/<id>.json
⑤ 返回 201 + updatedAt
```

| 操作 | 链路 |
|------|------|
| **创建** | `POST /secrets` → PUT 新对象 |
| **更新** | `PUT /secrets/<id>` → 覆盖写（版本控制保留旧版本） |
| **删除** | `DELETE /secrets/<id>` → DeleteObject（delete marker，可恢复） |
| **读取** | `GET /secrets/<id>` → GET 对象 → 客户端本地解密 |
| **导出备份** | `GET /export` → 全部密文信封（NDJSON）→ 客户端离线保管 |

## 5. 下载与同步链路

```
列表：GET /secrets → 应用服务 ListObjects → 返回清单（id/updatedAt）
拉取：GET /secrets/<id> → 应用服务 GET OSS 对象 → 返回密文信封
同步：客户端与本地缓存比对（id + updatedAt）得出新增/变更/删除差异 → 差异对象解密合并
```

- **全量同步即可**：小数据量下，客户端进入前台/手动刷新时同步，秒级完成
- **不需要** WebSocket 推送、sync_token 增量协议、changelog

## 6. 安全机制

| 机制 | 实现 |
|------|------|
| 传输加密 | 全链路 TLS 1.3 |
| 令牌验签 | JWKS 公钥验签 + exp/aud/iss 校验，无状态 |
| OSS 访问 | bucket 私有，应用服务用 STS 临时凭证（最小权限角色），客户端永不直接接触 OSS |
| 请求校验 | 对象 key 必须匹配 UUID 模式、信封大小上限（64 KB）、JSON schema 校验 |
| 内容完整性 | AES-GCM 认证标签，密文被篡改解密时立即失败 |
| 审计 | 应用服务日志记录每次读写（操作者、时间、对象 id、结果） |
| 泄露兜底 | 即便 OSS 全量泄露：无主密码无法派生密钥，密文不可解，且 OSS 侧 SSE-OSS 二次加密 |

## 7. 相比早期方案的取舍

| 早期设计 | 当前阶段处理 | 理由 |
|----------|-------------|------|
| presigned URL 直传/直下 | 砍掉，应用服务代理读写 | 无附件大文件，直传无收益，反而引入两套链路复杂度 |
| DEK 公钥包裹与分发 | 砍掉，主密码 KDF 派生单密钥 | 单团队个人模式，无共享需求 |
| WebSocket 推送 / sync_token 增量 | 砍掉，全量同步 | 小数据量，同步秒级完成 |
| 高敏条目二次确认 / 分片上传 | 后置 | MVP 不需要 |
| 乐观锁 / 冲突裁决 | 砍掉 | 忽略高并发，最后写入生效 |

## 8. 为将来预留的口子

| 未来需求 | 扩展方式 |
|----------|---------|
| 团队版权限细分 | JWT `scope` 字段已预留，无需改传输协议 |
| 团队共享 | 信封 JSON `encrypted` 结构升级为 DEK 信封加密（密钥来源从"派生"换"解包"），传输链路不变 |
| 大附件 | 届时再引入 presigned URL 直传，应用服务签发凭证，当前架构不受影响 |
| 高并发/多端一致性 | 引入 PG + 乐观锁 + 增量同步，密文对象零迁移 |
